# ADR-033: Reader Design Token Layer

- Status: Accepted
- Date: 2026-08-10
- Spec: `docs/specs/2026-08-09-song-presentation.md`
- Scope: `apps/lyron_app/lib/src/app/reader_theme.dart`, `apps/lyron_app/lib/src/app/app_theme.dart`, the song reader's content widgets (song_line_view.dart, song_reader_section_grid.dart, comment_line_view.dart, directive_line_view.dart, tab_block_view.dart), and `song_reader_char_metrics.dart`. Reader chrome (app bar, control bar, context bar, header, title bar, expanded-surface panels) is explicitly OUT of scope — still reads ambient ColorScheme directly, rebuilt in PR3.

## Context

The song reader's renderer (song_line_view.dart etc) and its fit estimator (song_reader_char_metrics.dart, via measureSongReaderCharWidths) each independently re-derived the same text styles by hand from `Theme.of(context).textTheme`/`.colorScheme` — e.g. both separately wrote `labelLarge.copyWith(fontWeight: w700, color: colorScheme.primary)` for the chord style, `bodyLarge.copyWith(height: 1.25)` for the lyric style. They agreed only by convention: nothing enforced that a change to one side stayed in sync with the other. The fit estimator's core invariant — `estimated height >= rendered height`, the guarantee that lets fit-to-screen never overflow — depends entirely on the two sides describing the same styles. A typography change to only one side would silently break that invariant. Separately: the app had no dark theme at all (`MaterialApp.router` set only `theme:`), tracked as UX-7 in the repository review, and dim-stage legibility was a real product need. A dark palette could not simply invert the light one — the light theme's accent green `#0B6E4F` sits near 2:1 contrast on black, unusable — so the two themes needed genuinely different value sets, which made a token layer a prerequisite rather than a nice-to-have.

## Decision

Introduce `ReaderTheme`, a Flutter `ThemeExtension<ReaderTheme>` (apps/lyron_app/lib/src/app/reader_theme.dart) carrying every colour and text style the reader's content surface uses: lyricStyle, chordStyle, chordChipColor, sectionLabelStyle, unknownSectionLabelColor, commentStyle, directiveStyle, leadingDirectiveStyle, tabStyle, tabBackgroundColor. Two factories build it: `ReaderTheme.fromM3` reproduces exactly what the widgets derived by hand before this ADR (used for the light theme, and as the fallback via `ReaderTheme.of(context)` for any `ThemeData` that hasn't registered the extension, e.g. older widget tests pumping a bare `MaterialApp`), and `ReaderTheme.stageDark` is a genuinely separate palette designed for a dim stage rather than an inversion. Both `buildLightTheme()` and `buildDarkTheme()` (apps/lyron_app/lib/src/app/app_theme.dart) register the extension via `ThemeData.copyWith(extensions: [...])`, and both are wired into `MaterialApp.router` via `theme:`/`darkTheme:` (apps/lyron_app/lib/src/app/lyron_app.dart), with an app-wide `ThemeMode` store/controller (apps/lyron_app/lib/src/app/theme_mode_store.dart) letting the reader's overflow menu switch between them explicitly, overriding the system default. Every reader content widget and `measureSongReaderCharWidths` now read styles via `ReaderTheme.of(context)` instead of re-deriving them. Spacing constants (song_reader_metrics.dart, song_reader_fit.dart) are deliberately NOT moved into the extension — they already live in one shared place, are theme-independent, and copying them in would recreate a second definition of something that already has exactly one.

## Consequences

- Typography changes now have exactly one edit point (`ReaderTheme.fromM3`/`ReaderTheme.stageDark`) that both the renderer and the estimator read — this is what the next PR in this slice (typography and spacing changes) depends on.
- A `ThemeData` that hasn't registered the extension falls back to `ReaderTheme.fromM3` over its own `ColorScheme`/`TextTheme`, pinned equal to the registered light theme's tokens by `apps/lyron_app/test/app/app_theme_test.dart`, so old tests and the light theme cannot silently drift apart.
- Reader chrome widgets (app bar, control bar, context bar, header, title bar, expanded-surface panels) still read `ColorScheme` directly and render Material-default rather than designed in dark mode — deliberately deferred to PR3 of this slice, which rebuilds the chrome.
- Closes UX-7 (no dark theme) from the repository review.
