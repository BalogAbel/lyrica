# ADR-033: Reader Design Token Layer

- Status: Accepted
- Date: 2026-08-10
- Spec: `docs/specs/2026-08-09-song-presentation.md`
- Scope: `apps/lyron_app/lib/src/app/reader_theme.dart`, `apps/lyron_app/lib/src/app/app_theme.dart`, the song reader's content widgets (song_line_view.dart, song_reader_section_grid.dart, comment_line_view.dart, directive_line_view.dart, tab_block_view.dart), and `song_reader_char_metrics.dart`. Reader chrome (app bar, control bar, context bar, header, title bar, expanded-surface panels) is explicitly OUT of scope — still reads ambient ColorScheme directly, rebuilt in PR4.

## Context

The song reader's renderer (song_line_view.dart etc) and its fit estimator (song_reader_char_metrics.dart, via measureSongReaderCharWidths) each independently re-derived the same text styles by hand from `Theme.of(context).textTheme`/`.colorScheme` — e.g. both separately wrote `labelLarge.copyWith(fontWeight: w700, color: colorScheme.primary)` for the chord style, `bodyLarge.copyWith(height: 1.25)` for the lyric style. They agreed only by convention: nothing enforced that a change to one side stayed in sync with the other. The fit estimator's core invariant — `estimated height >= rendered height`, the guarantee that lets fit-to-screen never overflow — depends entirely on the two sides describing the same styles. A typography change to only one side would silently break that invariant. Separately: the app had no dark theme at all (`MaterialApp.router` set only `theme:`), tracked as UX-7 in the repository review, and dim-stage legibility was a real product need. A dark palette could not simply invert the light one — the light theme's accent green `#0B6E4F` sits near 2:1 contrast on black, unusable — so the two themes needed genuinely different value sets, which made a token layer a prerequisite rather than a nice-to-have.

## Decision

Introduce `ReaderTheme` (apps/lyron_app/lib/src/app/reader_theme.dart) carrying every colour and text style the reader's content surface uses: lyricStyle, chordStyle, chordChipColor, sectionLabelStyle, unknownSectionLabelColor, commentStyle, directiveStyle, leadingDirectiveStyle, tabStyle, tabBackgroundColor. Two factories build it: `ReaderTheme.stageLight` (originally `fromM3`, renamed in PR3 — see below) reproduces exactly what the widgets derived by hand before this ADR (used for the light theme, and as the fallback via `ReaderTheme.of(context)` for any `ThemeData` that hasn't registered the extension, e.g. older widget tests pumping a bare `MaterialApp`), and `ReaderTheme.stageDark` is a genuinely separate palette designed for a dim stage rather than an inversion. Both `buildLightTheme()` and `buildDarkTheme()` (apps/lyron_app/lib/src/app/app_theme.dart) register the extension via `ThemeData.copyWith(extensions: [...])`, and both are wired into `MaterialApp.router` via `theme:`/`darkTheme:` (apps/lyron_app/lib/src/app/lyron_app.dart), with an app-wide `ThemeMode` store/controller (apps/lyron_app/lib/src/app/theme_mode_store.dart) letting the reader's overflow menu switch between them explicitly, overriding the system default. Every reader content widget and `measureSongReaderCharWidths` now read styles via `ReaderTheme.of(context)` instead of re-deriving them. Spacing constants (song_reader_metrics.dart, song_reader_fit.dart) were initially left out of the extension — they already lived in one shared place, were theme-independent, and copying them in would have recreated a second definition of something that already had exactly one.

**Amended 2026-08-12 (PR3 of this slice, the type scale).** The second half of that reasoning still holds: spacing does not vary by theme, and `ReaderTheme.stageLight` and `ReaderTheme.stageDark` are pinned to identical `SongReaderMetrics` by `reader_theme_test.dart`, so a theme swap cannot move a single pixel of layout. The first half did not survive the 600px type-scale breakpoint (`docs/specs/2026-08-09-song-presentation.md` section 7): row heights and gaps now differ between the phone and tablet/desktop sets, so they cannot be compile-time constants — and the value that resolves them is the same viewport width that resolves the type scale they have to match. Keeping them apart would have meant two independent breakpoint resolutions, which is the exact drift this extension exists to prevent, reintroduced one level up.

The constants therefore became `SongReaderMetrics` (song_reader_metrics.dart): one value object carrying every row height and gap the renderer and the estimator share, threaded through `song_reader_fit.dart` as a defaulted `metrics` parameter exactly the way `SongReaderFitTextScale` already was, and returned alongside the measured char widths by `measureSongReaderCharWidths`. There is still exactly one definition per value; it is now resolved rather than constant.

The registered extension is consequently `ReaderThemeSet`, holding a `compact` and a `regular` `ReaderTheme`, because `ThemeData` is built once at app start with no `MediaQuery` in scope. `ReaderTheme` keeps its name and its field names but is no longer a `ThemeExtension` — it is the *resolved* bundle for one breakpoint, which left every existing `ReaderTheme.of(context).lyricStyle` call site untouched. `ReaderTheme.of(context)` performs the resolution from `MediaQuery.maybeSizeOf(context)?.width`, and both the reader widgets and `measureSongReaderCharWidths` go through it with the same `BuildContext` — that single shared resolution point is what makes it impossible for the renderer and the fit estimator to see different row heights. With no `MediaQuery` at all it resolves to the regular set, deliberately: the regular set carries the larger type, so such a tree over-estimates rather than under-estimates, and only an under-estimate breaks the fit contract.

One further invariant came with the type scale: a row-height token and its text style must agree, because the estimator charges `lyricRowHeight` per rendered row while a `Text`'s real row height is `fontSize * style.height`. The token factories therefore DERIVE each style's `height` from its row-height metric instead of typing both as literals, and `reader_theme_test.dart` asserts the equality. Two independent literals there is the same class of drift as two independent copies of a style.

## Consequences

- Typography changes now have exactly one edit point (`ReaderTheme.stageLight`/`ReaderTheme.stageDark`) that both the renderer and the estimator read — this is what PR3 of this slice (typography and spacing changes) depended on.
- A `ThemeData` that hasn't registered the extension falls back to `ReaderTheme.stageLight` over its own `ColorScheme`/`TextTheme`, pinned equal to the registered light theme's tokens by `apps/lyron_app/test/app/app_theme_test.dart`, so old tests and the light theme cannot silently drift apart.
- Reader chrome widgets (app bar, control bar, context bar, header, title bar, expanded-surface panels) still read `ColorScheme` directly and render Material-default rather than designed in dark mode — deliberately deferred to PR4 of this slice, which rebuilds the chrome.
- Closes UX-7 (no dark theme) from the repository review.
- The reader's row heights and gaps are now breakpoint-dependent and resolved
  through `ReaderTheme.of(context)`. A widget that needs them must go through
  that call rather than importing a constant; `song_reader_metrics.dart` no
  longer exports any.
